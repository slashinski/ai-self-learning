## Goal

Parse the Devin CLI's session logs to extract this data automatically. Produce a structured audit trail (JSON or CSV) that traces any pipeline run — including failures — back to the exact step, model, token usage, and cost that produced it. This is the fifth and final Stage 4 certification artifact. Without per-step model, token, and cost data, your audit trail is an automatic FAIL — a trace that shows *what happened* but not *what it cost* does not measure cost-adjusted capacity.

---

## Background: Why Per-Step Cost Data Is Required

Stage 4 certification defines five artifacts. Four come from Module 5: the workflow definition, guardrails, punch-out evidence, and end-to-end success rate. The fifth — the audit trail — is what makes the workflow measurable in production.

"Cost-adjusted capacity" means you know what each step costs, not just whether it succeeded. When you run a 7-step pipeline and it fails at step 5, you need to know: which model was used at step 5? How many tokens did it consume? What did that step cost in ACUs and credits? Without that data, you are debugging in the dark — you can see *that* it failed, but not *what it cost to fail*.

The certification examiner checks for this explicitly. From the Stage 4 certification requirements:

> **Must include per-step model and token/cost data** — the audit trail (or an accompanying execution log) must record, for each step execution: which model was used, input tokens, output tokens, and cost (in dollars or ACUs). ... A trace with no per-step model/token/cost data is an automatic FAIL for this section.

This is not a nice-to-have. It is a hard gate. A beautifully structured audit trail that traces failures to their origin step but records zero cost data fails certification. The examiner needs to see, for every step in every run: model, prompt tokens, completion tokens, cached tokens, and cost.

## Background: Where the Data Lives

The Devin CLI records cost and token data in two places. Your harness will parse both.

### 1. Session Database (`sessions.db`)

The Devin CLI stores session metadata in a SQLite database at `~/.local/share/devin/cli/sessions.db`. Each session row contains a `cogs_json` field with cost data:

- `total_acu_cost` — the total ACU (Agent Compute Unit) cost for the session
- `total_credit_cost` — the total credit cost for the session

Each pipeline step that invokes `devin run` creates a session. You will query `sessions.db` to pull cost data for each step's session ID.

### 2. Transcript JSON Files

The Devin CLI writes transcript JSON files at `~/.local/share/devin/cli/transcripts/<session-id>.json`. Each transcript contains a `final_metrics` object with token data:

- `total_prompt_tokens` — input tokens sent to the model
- `total_completion_tokens` — output tokens generated by the model
- `total_cached_tokens` — tokens served from cache (reducing cost)

The transcript also identifies the model used for the session.

### What If You Use a Different Tool?

If you use Claude Code instead of Devin, the data sources differ: Claude Code writes JSONL logs to `~/.claude/projects/` with per-message token usage and model identifiers. If you use GitHub Copilot, consult its CLI logging documentation. The audit trail structure is the same regardless of tool — only the parsing logic changes. The certification requirement (per-step model, tokens, cost) is tool-independent.

## Step 2: Add Step-Level Logging to Your Harness (45 minutes)

Your Module 5 harness already runs the 7-step pipeline. Now add logging so that each step records its session ID, timestamps, and status. You will use this log to correlate steps with cost data in the next step.

Add a logging function to your harness script that writes a structured entry for each step:

```bash
log_step() {
  local step_name="$1"
  local session_id="$2"
  local status="$3"
  local start_time="$4"
  local end_time="$5"
  local output_file="$6"

  echo "{\"step\": \"$step_name\", \"session_id\": \"$session_id\", \"status\": \"$status\", \"start_time\": \"$start_time\", \"end_time\": \"$end_time\", \"output_file\": \"$output_file\"}" >> "$AUDIT_LOG"
}
```

Wrap each pipeline step invocation with start/end timestamps and capture the session ID that Devin returns. The session ID is critical — it is the key that joins your step log to the cost data in `sessions.db` and the token data in the transcript files.

**What to log for each step:**

| Field | Source | Why |
|-------|--------|-----|
| `step` | Your harness (step name) | Identifies which pipeline step ran |
| `session_id` | Devin CLI response | Joins to `sessions.db` and transcript files |
| `status` | Your harness (success/fail) | Failure traceability |
| `start_time` | `date -u` before step | Duration measurement |
| `end_time` | `date -u` after step | Duration measurement |
| `output_file` | Your harness (output path) | Links to the artifact produced |
| `error_message` | Your harness (if failed) | Failure root cause |

Run your harness once with the logging in place. Verify that `audit-log.jsonl` (or whatever you name it) contains one entry per step, with valid session IDs.

## Step 3: Write the Cost Data Parser (60 minutes)

Now write a script that reads your step log, queries `sessions.db` and the transcript files for each session ID, and produces a combined audit trail with per-step model, token, and cost data.

Create `parse-audit-trail.py`:

```python
#!/usr/bin/env python3
"""
Parse Devin CLI session logs and produce a structured audit trail
with per-step model, token, and cost data.

Reads:
  - Step log (JSONL from your harness)
  - ~/.local/share/devin/cli/sessions.db (SQLite — cogs_json with cost)
  - ~/.local/share/devin/cli/transcripts/<session-id>.json (token data)

Writes:
  - audit-trail.json (structured audit trail with all fields)
  - audit-trail.csv (same data in CSV format for spreadsheet analysis)
"""

import json
import sqlite3
import sys
import csv
from pathlib import Path

SESSIONS_DB = Path.home() / ".local/share/devin/cli/sessions.db"
TRANSCRIPTS_DIR = Path.home() / ".local/share/devin/cli/transcripts"

def load_step_log(path):
    """Load the JSONL step log produced by the harness."""
    steps = []
    with open(path) as f:
        for line in f:
            line = line.strip()
            if line:
                steps.append(json.loads(line))
    return steps

def query_session_cost(session_id):
    """Query sessions.db for cogs_json cost data."""
    conn = sqlite3.connect(str(SESSIONS_DB))
    cursor = conn.cursor()
    cursor.execute(
        "SELECT cogs_json FROM sessions WHERE session_id = ?",
        (session_id,)
    )
    row = cursor.fetchone()
    conn.close()

    if not row or not row[0]:
        return {"total_acu_cost": None, "total_credit_cost": None}

    cogs = json.loads(row[0])
    return {
        "total_acu_cost": cogs.get("total_acu_cost"),
        "total_credit_cost": cogs.get("total_credit_cost"),
    }

def query_transcript_metrics(session_id):
    """Read transcript JSON for token counts and model name."""
    transcript_path = TRANSCRIPTS_DIR / f"{session_id}.json"
    if not transcript_path.exists():
        return {
            "model": None,
            "total_prompt_tokens": None,
            "total_completion_tokens": None,
            "total_cached_tokens": None,
        }

    with open(transcript_path) as f:
        transcript = json.load(f)

    metrics = transcript.get("final_metrics", {})
    # The model name may be in final_metrics or at the top level —
    # inspect your actual transcript structure (Step 1) and adjust.
    model = metrics.get("model") or transcript.get("model", None)

    return {
        "model": model,
        "total_prompt_tokens": metrics.get("total_prompt_tokens"),
        "total_completion_tokens": metrics.get("total_completion_tokens"),
        "total_cached_tokens": metrics.get("total_cached_tokens"),
    }

def build_audit_trail(step_log_path, output_json, output_csv):
    """Combine step log + cost data + token data into a structured audit trail."""
    steps = load_step_log(step_log_path)
    audit_entries = []

    for step in steps:
        session_id = step.get("session_id")
        if not session_id:
            print(f"WARNING: step '{step.get('step')}' has no session_id — skipping cost lookup",
                  file=sys.stderr)
            cost = {"total_acu_cost": None, "total_credit_cost": None}
            tokens = {
                "model": None,
                "total_prompt_tokens": None,
                "total_completion_tokens": None,
                "total_cached_tokens": None,
            }
        else:
            cost = query_session_cost(session_id)
            tokens = query_transcript_metrics(session_id)

        entry = {
            "step": step.get("step"),
            "session_id": session_id,
            "status": step.get("status"),
            "start_time": step.get("start_time"),
            "end_time": step.get("end_time"),
            "duration_seconds": None,  # calculate if timestamps are ISO format
            "model": tokens["model"],
            "prompt_tokens": tokens["total_prompt_tokens"],
            "completion_tokens": tokens["total_completion_tokens"],
            "cached_tokens": tokens["total_cached_tokens"],
            "total_tokens": (
                (tokens["total_prompt_tokens"] or 0)
                + (tokens["total_completion_tokens"] or 0)
            ) if tokens["total_prompt_tokens"] is not None else None,
            "acu_cost": cost["total_acu_cost"],
            "credit_cost": cost["total_credit_cost"],
            "output_file": step.get("output_file"),
            "error_message": step.get("error_message"),
        }
        audit_entries.append(entry)

    # Write JSON
    with open(output_json, "w") as f:
        json.dump(audit_entries, f, indent=2)

    # Write CSV
    if audit_entries:
        fieldnames = list(audit_entries[0].keys())
        with open(output_csv, "w", newline="") as f:
            writer = csv.DictWriter(f, fieldnames=fieldnames)
            writer.writeheader()
            writer.writerows(audit_entries)

    return audit_entries

if __name__ == "__main__":
    import argparse
    parser = argparse.ArgumentParser(description="Build audit trail from step log and Devin session data")
    parser.add_argument("step_log", help="Path to the JSONL step log from the harness")
    parser.add_argument("--output-json", default="audit-trail.json", help="Output JSON path")
    parser.add_argument("--output-csv", default="audit-trail.csv", help="Output CSV path")
    args = parser.parse_args()

    entries = build_audit_trail(args.step_log, args.output_json, args.output_csv)
    print(f"Audit trail: {len(entries)} entries written to {args.output_json} and {args.output_csv}")
```

**Important:** The code above is a starting point. The exact field names in `cogs_json` and `final_metrics` may vary by Devin CLI version. You discovered the actual structure in Step 1 — adjust the parser to match your real data. If a field is named differently in your version, change the parser. If a field is missing entirely, record `null` and document the gap.

Run the parser against your step log from Step 2:

```bash

```

Verify the output contains entries for all 7 pipeline steps with populated model, token, and cost fields.

## Step 4: Handle Missing Data Gracefully (30 minutes)

In practice, some steps will have missing cost data. This happens when:
- The Devin CLI session failed before writing to `sessions.db`
- The transcript file was not written (crash, timeout)
- The session ID was not captured by your harness (bug in logging)
- You are running a step that does not invoke the Devin CLI (a local shell step)

Your audit trail must handle these cases explicitly. A `null` in the cost field is acceptable if it is documented — a silent omission is not.

Add a validation pass to your parser that checks each entry and reports gaps:

```python
def validate_audit_trail(entries):
    """Check for missing data and report gaps."""
    issues = []
    required_fields = ["model", "prompt_tokens", "completion_tokens", "acu_cost"]

    for i, entry in enumerate(entries):
        for field in required_fields:
            if entry.get(field) is None:
                issues.append(
                    f"Step '{entry.get('step')}' (entry {i}): "
                    f"missing '{field}' — session_id: {entry.get('session_id')}"
                )

    if issues:
        print("VALIDATION ISSUES:", file=sys.stderr)
        for issue in issues:
            print(f"  - {issue}", file=sys.stderr)
    else:
        print("All entries have complete cost data.", file=sys.stderr)

    return issues
```

Call `validate_audit_trail(entries)` at the end of `build_audit_trail`. Any gaps should be investigated and either fixed (if they are bugs in your logging) or documented (if they are genuine data source limitations).

Create `audit-trail-gaps.md` documenting any steps where cost data is missing and why. If there are zero gaps, write that down too — "all 7 steps have complete model, token, and cost data across all runs" is a strong certification signal.

## Step 6: Verify Against the FAIL Condition (20 minutes)

The Stage 4 certification has an explicit automatic FAIL condition for the audit trail:

> Audit trail has no per-step model/token/cost data — cannot measure cost-adjusted capacity

Run this self-check against your audit trail before moving on. For each of the following, verify the answer is "yes":

1. **Does every step entry have a model field?** Open `audit-trail.json` and check that no entry has `"model": null` (unless you documented why in `audit-trail-gaps.md`).

2. **Does every step entry have prompt and completion token counts?** These should come from `final_metrics` in the transcript files.

3. **Does every step entry have cost data (ACU and/or credit)?** These should come from `cogs_json` in `sessions.db`.

4. **Can you trace a failure to its origin step?** If any of your 3 runs failed, open the audit trail for that run and find the failed step. Does the entry show the model, tokens, and cost at the point of failure? If all runs succeeded, deliberately introduce a failure (bad input, missing file) and run once more to test traceability.

5. **Does the audit trail cover ALL steps?** Count entries in `audit-trail.json` — there should be 7 per run (one per pipeline step). If any step is missing, your harness logging has a gap.

If any check fails, go back and fix the logging or parsing before proceeding to Exercise 23. An audit trail that passes 4 of 5 checks is still a FAIL — all five must pass.
